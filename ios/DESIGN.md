# DOT DROP — iOS ネイティブ移植

## 方針

- **App Store 審査を通すため、ネイティブ（SwiftUI + 自前 Engine）で実装する**
- WKWebView で HTML を包む方式は使わない（申請で弾かれやすい）
- **見た目・配置・物理の正本は `index.html`**
  - 色・余白・HUD は CSS の数値を写す（`Theme` / `GameHUD` / `TitleView`）
  - 物理は `/*ENGINE*/` を `DotDropEngine` に移植（数値の独自調整はしない）
  - 盤面は `draw()` の順と色に合わせる（`BoardCanvas`）

## 構成

```
ios/DotDrop/App/
  Theme.swift        … :root / fit()
  GameSession.swift  … フリープレイ進行
  TitleView.swift    … #start
  GameHUD.swift      … <header>
  BoardCanvas.swift  … canvas draw
  ResultOverlay.swift… #over / #sheet
  RootView.swift     … overlay 切り替え
DotDropEngine/       … ENGINE + フィクスチャテスト
```

## レイアウト注意

- `RootView` は全画面 `fit()` のため `.ignoresSafeArea()` する。そのままだと
  `GeometryReader.safeAreaInsets` が 0 になり、HUD が Dynamic Island にめり込む。
  → `ScreenSafeArea`（UIWindow の insets）を使い、CSS の `env(safe-area-inset-*)` と同じ値を渡す
- タイトルの O は固定サイズの Canvas アニメ。`alignmentGuide` は使わない（AttributeGraph cycle）
- `GameSession` は `@Observable`。`pullX/Y` と `engine` は `@ObservationIgnored`
  （ドラッグや物理のたびに RootView 全体が再構築されないようにする）
- `BoardCanvas` の `TimelineView` は **`timeline.date` を Canvas 内で読む**こと。
  読まないと Canvas が再描画されず、受け皿も脈打ちも止まる
- 発射 Y は帯と同じくノッチ分だけ下げる（上限 26）。STAGE と玉の重なり防止

## フィーバー（Web と同じ）

- 釘ヒットのポイントを `gauge` に加算（受け皿倍率は含めない）
- `FEVER_AT = 120` で、打ち終わり（`shotEnd`）に突入、`FEVER_SHOTS = 3`
- ▲ 連鎖で1回の放出でも 120 を超えやすい（仕様どおり。早すぎる感じが出やすい）

## 移植でつまずいた所（実機で遊んで分かったもの）

同じ数値を写しても、同じ感じにならなかった所。**次に何かを移すときは、まずここを疑う。**

### 音

- **`floatChannelData?[0]` だけに書かない。**左チャンネルにしか音が入らず、
  イヤホンでは片耳、スピーカーでも半分の大きさになる。必ず全チャンネルに書く
- **`voice` の波形を省略しない。**本家は第4引数で形を指定している
  （減る受け皿＝ノコギリ／×0＝サイン／倍率と■＝矩形／●＝サイン）。
  全部を三角波にすると、減ったときの「ブー」がただの低い音になって残念さが出ない
- **節目の音を、釘の音と同じ経路で鳴らさない。**必ず埋もれる。別のバス（`fan`）に、
  ブラスとベルで、残響をかけて鳴らし、その間は釘の音を下げる（ダッキング）。
  本家が経路を分けているのは、まさにこの指摘への対策
- **ローパスの Q を落とさない。**本家のブラスは Q=2 の共振つきで、カットオフの
  あたりが持ち上がって金管の芯になる。1次のローパスにすると山も全体も痩せる（実測で1/3）

### 文字

- **`Font.custom(_:size:)` は端末の文字サイズ設定で勝手に拡大される。**
  必ず `fixedSize:` を使う。設定を大きめにしている人の画面で、数字が枠から溢れて切れる
- **`tracking` ではなく `kerning`。**`tracking` は最後の文字のうしろにも詰めを入れるので、
  負の値だと右端の1文字が欠ける
- **文字の幅は測る。**「文字数 × 係数」で見積もらない。日本語は1文字がほぼ倍の幅なので、
  説明文の幅が大きく外れる。幅から位置を決めている区切り線も、かぶったり離れたりする
  （`GraphicsContext.resolve(_:).measure(in:)` で測れる）
- **SF Pro は Helvetica Neue より細く小さく見える。**同じ pt でも印象が変わるので、
  盤面・HUD・結果画面は Helvetica Neue に揃える（`DD.bold` / `DD.regular`）
- 持ち玉・スコアの大きさは、縮む任せ（`minimumScaleFactor`）にしない。
  本家の `Roller.fit()` と同じ計算で決める（画面の半分 − STAGE の半分 − 32、1桁 .57em、上限46）

### 板（ボトムシート）

見た目を似せるだけでは足りない。**下から滑り出す／指についてくる／70px より下で閉じる**
まで入れて、はじめて「どうやって戻るのか」が分かる。角を丸めるのは上だけ、下は画面の端まで
（下も丸めると、浮いた札に見えて板にならない）。

### 結果画面

`.result > * { width:100%; max-width:320px }` で、中身がすべて 320px に揃う。
**「もう一度」と「タイトルへ」は同じ幅。**文字幅ぶんの padding にすると幅が変わる。
なおタイトル画面のほうは本家も揃えていない（153.7 と 147）。

### 発射位置は固定値にしない

本家の `LAUNCH.y = 140` は**本家の HUD の高さを前提にした数字**で、そのまま持ってくると合わない。
ネイティブは STAGE の列（STAGE／数字／6つの丸）が本家より約6pt 高く、丸が下へ来るので、
待機中の点線の弧（玉の中心から上へ34）とリングが丸を食う。

`applyFit` で HUD の下端から決める：

```
HUD の下端 = safe-area-inset-top + 38（ヘッダーの余白）+ 46（STAGE の列・実測）
発射位置   = max(140, HUD の下端 / 拡大率 + 34 + 8)
釘の上端   = 発射位置 + 60   ← 本家と同じ間隔
```

ノッチのない端末では 140 に収まり、本家と同じ位置になる。実測（弧の頂点と丸の下端の間）：

| 端末 | 玉 | 弧の頂点 | 丸の下端 | あき | 釘 |
|---|---|---|---|---|---|
| Dynamic Island 393 | 189pt | 152pt | 143pt | 9pt | 10行 |
| ノッチあり 390 | 176pt | 140pt | 131pt | 9pt | 10行 |
| ノッチなし 375 | 148pt | 112pt | 104pt | 8pt | 8行 |

**釘の行数は成り行きでよい。**玉が STAGE に被らないことのほうが大事、というのが作者の判断。
ただし `field()` の下端に上限を付けてはいけない（1行減って、そのぶんが受け皿の上の余白になる）。

### 設定（音・振動・演出）はタイトルの右上

**リセットの板には入れない。**あちらは「やめるかどうか」を聞く場で、設定とは用事が違う。
キャンセルの下に別の操作が付くと、板の終わりも分からなくなる
（板の中身は［見出し］［ひとこと］［リセット］［タイトルに戻る］［キャンセル］の5つ）。

タイトル画面の右上に小さなしるしを置き、押すと同じ形の板が下から出る。
「はじめる」「あそびかた」の2つは主役のまま動かさない。

入口は **iOS の歯車（`gearshape`）**。「形は丸と四角と三角だけ」の例外。

順に試した結果：
1. 丸だけで組んだ印（点の列を3行、各行1つだけ赤）… 「何を指しているか分からない」
2. 枠つきの「設定」という文字（リセットと同じ形）… 伝わるが、作者は歯車を選んだ
3. **iOS の歯車** … 覚えて使う記号なので、形の理屈より通りがよい

歯車は Liquid Glass の丸ボタンに乗せる。色は世界観に寄せて**マスタードの薄い色味**（22%）。
赤は「はじめる」が使っているので右上の小さなものに使うと主役とぶつかる。
白（クリーム）は玉の色なので単色では使わない。残るのがマスタード。

**Liquid Glass は iOS 26 から。**古い Xcode には API 自体が無いので `compiler(>=6.2)`
でも切り分けている。それ以前では、同じ丸にマスタードの薄い地と細い枠を敷いた形になる
（CI の macos-15／Xcode 16 が通るのはこちら）。

抽象的な印を自作しても伝わらない、というのはこの作品で二度目（リセットのボタンが一度目）。

中身は3つ。どれも実際に効く。
- **サウンド** … 釘の音・節目の音・歓声が止まる
- **振動** … 振動が止まる
- **点滅・揺れを抑える** … 画面の揺れが0になり、数字ドンの飛び込みと赤・黄・青の
  高速入れ替えが止まる。iOS の「視差効果を減らす」でも同じ状態になる

## 間の取り方は本家に合わせない

**`index.html` が正本なのは、物理とルールと色と形まで。**余白や間隔は、実機で見て
「詰まっているか、そうでないか」で決める。本家と同じ数字でも、詰まって見えるなら直す。

Safari とネイティブでは文字の行の高さが違う（CSS の `line-height: normal` は
文字サイズの約1.33倍、SwiftUI の `Text` は約1.17倍）。同じ数字を入れても同じ空きには
ならないので、数字を合わせにいくこと自体が意味を持たない。

タイトル画面の例。全部を似た間隔にすると、4つが一つの塊に見えて詰まる。

```
DOT DROP
   ↓ 22   タイトルと ■●▲ は同じまとまり
■ ● ▲
   ↓ 56   ここが「見せるもの」と「操作」の境目。いちばん大きく空ける
[ はじめる ]
   ↓ 28   2つのボタンは組。だが、くっつけない
[ あそびかた ]
```

設定の歯車は、端との空きを **20** にする（画面の中の持ち玉・スコアと同じ空け方）。
8 だと画面のふちに貼りついて見えた。上も `safe-area + 8` で、ゲーム中のリセットと揃える。

## タイトルから記録を見る

CLAUDE.md には「ランキングや記録はタイトルには出さない」とあるが、**押して開く形なら出す**。
はじめる前に読むものが増えるのが嫌なのであって、見たいときに見られないのは別の話。

左上にトロフィー（設定の歯車と対になる形・同じガラスの丸）。押すと**下から板**。
板の中は**ベストスコアが主役**。いちばん大きく出して、結果画面と同じリールで0から回す。
その下にランキング上位5件とこれまでの記録（結果画面と同じ部品 `RecordsSections`）。
**2か所で作り分けないこと。**結果画面は今回の回をマスタードで塗る、こちらは塗りなし、の違いだけ。

板の中に一覧があるので、**指で引けるのは上の見出しの部分だけ**にする。
板ごと引けるようにすると、一覧のスクロールと取り合いになる。

## 結果画面の大きなスコア

**ゲーム中の持ち玉・スコアと同じリール（`RollingNumber`）で回す。**
ただの数字の差し替えにすると、画面が変わったときに見せ方が変わってしまう。

大きさは**リールの1枠 .57em を物差しに**して、入る値まで落とす。
文字幅で測ったり `minimumScaleFactor` に任せたりすると、測った幅と描く幅がずれて
右端が欠ける（`monospacedDigit()` を custom フォントに掛けるのも同じ理由でだめ）。
